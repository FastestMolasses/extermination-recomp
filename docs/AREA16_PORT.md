# AREA16's overlay owners (lane PORT-A16)

Lane PORT-A16, 2026-11-17, branch `a16`. AREA16 (area byte 0x10, overlay
id 0x0D, `OVERLAY/AREA16.BIN`; subs 0 and 1) is behind AREA06 sub 1's door
[3] (SECOND_HALF_AREAS.md section 4). The translations are proven against
the original instructions over designed states; since lane PORT-LIVE-A16 the
area also loads live from Claude's guided run (section "Live").

## What is translated

`src/game/em_area16_overlay*.c` (`em_area16_overlay.h`; plumbing in
`em_area16_overlay_internal.h`, the hook block and wrappers generated by
`tools/gen_area16_overlay.py`) translates every overlay behaviour the
placements and groups of AREA16 name, from the decomp's C under
`src/overlays/AREA16/` (decomp docs/AREA16_OVERLAY.md):

| File | Functions (runtime addresses) |
|---|---|
| `em_area16_overlay.c` | 0x823580 (group 0x829750 [4..8]), 0x8261A0 (s0[11]), 0x826C50 (s1[44..46]), 0x827030 (s1[42], [43]) |
| `em_area16_overlay_b.c` | 0x824440 (s1[39]) with 0x824540 and 0x825660; 0x824690 (s1[11], NEARMISS) with its child behaviour 0x825260, script 0x829970's op09 0x825630 and the helpers 0x825670, 0x8256E0, 0x825730, 0x825780; 0x824E10 (groups 0x829660 [1], 0x829750 [3]) |
| `em_area16_overlay_c.c` | 0x825800 (s0[10], the player's height mover; both 0019C6F0 calls: (0x28, 1) and (0x28, 0)) with 0x826A50 and scripts 0x82A1C0 / 0x82A3C0's op09 0x826C20 |
| `em_area16_overlay_d.c` | 0x8273F0 (s0[9], s1[13..27]; both 001A2370 calls) with its child behaviour 0x828200, 0x827B70 (s1[41]), 0x827CE0 (s1[28], [29]), 0x827FA0 (s1[30..34]) |
| `em_area16_overlay_e.c` | 0x8263D0 (s0[13]), 0x825310 (s1[10], NEARMISS) |
| `em_area16_overlay_f.c` | the effect behaviours 0x8237A0 (NEARMISS), 0x8239B0, 0x823D20, 0x823F70, 0x824110 (lane PORT-A16FX, section "Effects") |

Where the decomp C is NEARMISS (0x824690, 0x825310), the translation
follows the original's access order and the oracle runs the original
words, so it decides.

**Effects:** see section "Effects" (lane PORT-A16FX). The init 0x824420 is the
second-half state's (section 1 of SECOND_HALF_AREAS.md).

**Two caller-register arms (fail-stop).** 0x823580 with +0x94 outside
0xA..0xE, and 0x828200 in state 1 with +0xD outside 6 / 0x25 / 0x14,
assign nothing in the original: it goes on with the registers its caller
left (the size, count and rate; the part count). That is not reproducible,
so the native latches `EM_AREA16_OVERLAY_FAULT_CALLER_REGISTER` (6) at
the function's address there. The spawners give 0x828200 only +0xD 6,
0x25 or 0x14 (0x8273F0, 0x827B70). Which +0x94 values 0x823580's group
records carry is unchecked.

**Overlay data addresses.** The decomp's `D_overlay_AREA16_*` data names
are runtime addresses (the oracle confirms each one the code uses); only
the function names are link addresses (runtime less 0x40).

## Evidence

`make test-area16-overlay-reference` (`tools/test_area16_overlay_reference.py`,
cases in `tools/area16_overlay_cases_{a..e}.py`): the shared harness
(`tools/test_level14_port_reference.py`) configured as
test_level17_boot_reference configures it for AREA21's twins. The user's
whole AREA16.BIN (header, text, data) is loaded over the arena of capture
a03b_03_item2a (its AREA03 text and boot text first checked against the
user's files), the first 0x1000 bytes of AREA16's BSS are zeroed, and each
entry runs over designed nodes in zero RAM. Every callee is a hook with a
scripted result except the vector / matrix helpers and the sine, which run
as original code. Compared per case: calls and arguments, memory at every
call, the memory accesses between calls one for one in order, memory
after, a poisoned re-run, every reachable original word, the callee
inventory and the fail-stop contract; plus the two caller-register
fail-stops checked natively.

- Quick run: 2018 cases, about 6 s; `EM_TEST_FULL=1`: 2193 cases. Both pass
  (with the five effect behaviours of section "Effects").
- Every reachable word of the 30 entries runs, but two delay-slot words of
  the caller-register arms (0x82361C, 0x8282F8), named DEAD in the cases.

  script address) fails the run (19 failures).

## Water grid (lane PORT-WATER, 2026-11-17)

Branch `water`. [10] 0x825800 (sub 0, the player's height mover) drives
the water barrier's grid through six boot functions; they are translated
in `src/game/em_area16_water.c` (`em_area16_water.h`, plumbing in
`em_area16_water_internal.h`, hook block and wrappers generated by
`tools/gen_area16_water.py`) from the decomp C:

| Function | What it does | Decomp |
|---|---|---|
| 001DAFA0 | zeroes every cell's velocity and height, sets the block's rates and origin | byte-matched |
| 001DB240 | the stage byte 0x81C011 | byte-matched |
| 001DB250 | per-frame stage step (jump table of 7; the shade words ease toward 0xC0 from stage 3), then 001DB040 below stage 6 | byte-matched |
| 001DB040 | one wave step of the 32 x 32 grid, a random impulse, heights clamped at 70 | NEARMISS (register colouring only) |
| 001DB480 | the grid's GS display list: 31 strip packets of 64 vertices, kicked through 001CAAC0 | byte-matched |
| 001DAE10 | one vertex: screen point by 0x70003AC0, VU0 clip by vf24..vf27, reject flags | byte-matched (inline VU0) |
| 001DAC90 | the vertex record (colour, fog, s/t/q, 12.4 screen x/y/z) | NEARMISS (register colouring only) |

other modules' model (denormals as zero, a lane with exponent 255 faults
`EM_AREA16_WATER_FAULT_UNMEASURED`). For the two NEARMISS functions the
access order follows the original instructions; the oracle decides.
